The problem

Teams hand AI agents live cloud credentials. Logs and receipts are written by the same trust root that acts. Plumbline lets you attack an agent that owns a real Vultr account and checks the result against Vultr itself.

Admission checklist for a buyer

  1. The agent process holds no credential (see the sandbox env on Proof).
  2. A dollar ceiling the agent cannot raise (try "provision a 64 vCPU node").
  3. A verifier on a different host and key (Reconcile).
  4. A kill-switch that works when the primary host is dead.
  5. Policy is versioned data with tests; production changes need a signature (Policy).

We do NOT claim

  • That create-then-delete is prevented: the verifier is point-in-time.
  • That the spend shown is Vultr's invoice: it is broker arithmetic from public prices.
  • That the model resists attacks: the demo model is told to follow whatever you ask (compliant-operator mode), so you are testing the policy engine, not the model's caution.
  • That the sandbox is a microVM or unescapable: it is a hardened container.
  • That VM deletion can be reversed: only Object Storage versioning can.
  • That a bond deters a model.
  • That your policy edits change production: they change your own copy.
  • That ACL tiers give per-resource scoping: Vultr has none; the engine is the fine-grained control.

Terms in plain words

Broker
The one process that holds the cloud credentials. The agent never does; it can only ask the broker.
Policy engine
Code that answers every request with ALLOW, ESCALATE or DENY and the rule that decided it. It is not a model.
Floor
The production rules nobody can edit from the sandbox. Your own policy copy can be stricter or looser, but the floor is always applied too.
Escalate
Held for a person. Nothing runs until someone approves it, and an approval is re-checked against the live account.
Verifier
A second host in another region with a read-only key. It reads the live account and compares it to the ledger. GREEN, RED naming the resource, or DEGRADED when it cannot tell.
Watchdog
Runs next to the verifier. If the broker stops renewing its lease, it destroys the agent's workers and playgrounds, and nothing else.
Tier
The access level of the key the agent uses. Observer is read-only, and Vultr itself refuses writes.
Ceiling
A dollar limit per session and overall that the agent cannot raise. It is checked before any call to Vultr.
Bond
A small risk budget. An approved delete with no restore point burns it, and while it is low, new provisions are refused.
Rewind
The one live undo: Object Storage keeps versions, so a deleted object can be restored.
Compliant-operator mode
The demo model is instructed to follow the attacker's request. That is deliberate: it makes the policy engine, not the model's own caution, the thing being tested.
Rung and gate
A rung is one safety claim. Its gate is the live test that proves it against the real account and writes an evidence file.
Drift
How far the live account is from what the policy says it should be. No drift means they match.

What this release is, and is not

This is a working reference implementation plus a live demo range: the engine, broker, sandbox, verifier, watchdog and ledger run on real Vultr infrastructure, and you can run all of it on your own account (Run it yourself).

It is not yet a hosted team product. There is no web wizard to connect your account (setup is a command), no standing approval queue with notifications, no alerting, no spend history per agent, and no multi-account or single sign-on. Those are the next layer, not part of this release.

Vultr services used

Cloud Compute (two VMs and the protected target), Serverless Inference (three models), IAM sub-user ACLs with IP allow-lists, Firewall groups, VPC, Container Registry, Object Storage with versioning, the public plans rate card.
