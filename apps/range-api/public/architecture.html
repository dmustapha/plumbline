The components

The agent never holds a cloud credential. Every action it wants is a request to the broker, the broker asks a policy engine, and only an ALLOW reaches your Vultr account. A second host in another region checks the account independently of the broker.

The picture in words: the agent runs in a sandbox with no credentials and one route out. The broker holds every key and contains the policy engine, the spend meter, the ledger and the Vultr adapter. A verifier and a watchdog on a second host read the live account and the ledger export, and can destroy the agent's workers if the broker stops renewing its lease.

One request, start to finish

  1. The agent writes code that wants to act, for example delete an instance. The code runs in a throwaway container with no credential, no internet and one route.
  2. The relay forwards only POST /v1/call with a short-lived task token and the request: a verb, a resource class, a target id and parameters.
  3. The broker checks the token and resolves the facts about the target from the live account. Labels or tags the agent supplies are discarded.
  4. The policy engine decides. The production floor and the session policy are both evaluated and the most restrictive answer wins. The result is ALLOW, ESCALATE or DENY plus the rule id that decided it.
  5. The spend meter checks the dollar ceiling before any network call. An action that would exceed it is denied.
  6. Only an ALLOW reaches Vultr. The adapter will not run without a decision value only the engine can create. An ESCALATE is held for a person. A DENY does nothing.
  7. The ledger records the decision. Only the engine path can write a row, and rows are never edited.
  8. The verifier re-reads the account from another host with its own read-only key, twice, three seconds apart, and compares it to the ledger and to an owner baseline.
  9. If the broker dies, its lease lapses and the watchdog destroys the agent's workers and playgrounds. It never touches production or infrastructure.

Trust boundaries

BoundaryWhat can crossWhat cannot
Sandbox to brokerOne request route with a task tokenCredentials, the network, the filesystem of the host
Broker to VultrCalls with an ALLOW decision, through tiered IP-locked keysAny call the engine did not allow
Public app to brokerSession requests and read-only views over a private socketAny Vultr, inference or storage key
Verifier to VultrRead-only listingAny write
Verifier to brokerA signed ledger exportTrust: it checks the export against the live account

What this does not cover: a compromised broker process holds keys that can destroy any instance in the account, because Vultr has no per-resource scoping. The IP lock, the tiered keys, the verifier on another host and the watchdog are defence in depth. See the Safety model for the full list.
