Run it on your own Vultr account

The demo range runs on an account we own. Everything you attacked there is the same software you can run on yours: the policy engine, the broker that holds the keys, the hardened sandbox, the second-region verifier and the watchdog.

Setup today is a short command-line procedure on your own machine, not a web wizard.

What you run

  • Broker VM (one region): the public app, the broker that holds every key, and the sandbox runner. Three services.
  • Verifier VM (a second region): the verifier and the watchdog, each with its own scoped key.
  • A protected production resource the agent must not touch, and a versioned Object Storage bucket for the Rewind scene.
  • Six IP-locked sub-user keys, one per access tier, each with an explicit expiry.

Cost: about $25 a month for the two VMs, plus Serverless Inference usage, which the broker meters against a dollar ceiling. We ran the demo on the Vultr event credit.

Set it up

  1. Clone the repository and install: git clone https://github.com/dmustapha/plumbline && cd plumbline && npm ci
  2. On your machine, with your owner API key in the environment, create the infrastructure: npm run bootstrap:range. It is idempotent and prints only a summary.
  3. Install the systemd units from ops/systemd/ on the two VMs and start them.
  4. Sign your production policy with your own key: npm run sign-policy. Production changes need that signature.
  5. Prove each rung on your account: npm run gate -- l1 through l7. Each writes an evidence file.
  6. When you are done: npm run teardown lists everything it created and deletes only with --yes.

Where your keys live

  • Only on the broker VM, in a root-owned environment file. Never in the agent, the sandbox or the browser.
  • Your owner key never goes on a VM. Every service refuses to start if it finds one.
  • The agent talks to the broker over one route. It can ask; it cannot read.

Write your policy

Rules are data in a YAML file you can review, test and version. This is a real rule from the production floor:

- id: floor-prod-immutable
  effect: deny
  priority: 95
  match: { verb: [delete, update], class: [instance, firewall_group, vpc, registry], label_prefix: [plumbline-prod-, plumbline-infra-] }
  reason: "production floor: not editable without a signed approval"

Your own session policy can be stricter or looser, but the floor is always applied too, and the most restrictive answer wins. Try this on the Policy page of the demo.

Approvals

When a rule says ESCALATE, the action is held. An approval is bound to that decision and a one-time token, is re-checked against the live account at the moment you approve, and cannot override a floor DENY. Today approvals are handled on the range page for the session that made the request.

Audit your account

The verifier ships as a command that reads your account with a view-only key and a ledger export, and writes nothing to Vultr:

PLUMBLINE_VERIFY_KEY=<view-only key> npx tsx apps/verifier/src/cli.ts --ledger ledger.json --baseline baseline.json
# exit 0 GREEN, 1 RED, 2 DEGRADED

The broker serves a signed ledger export at /ledger/export. The same check runs live on the Reconcile page.

What you get today, and what you do not

Today: the engine, broker, sandbox, verifier, watchdog and ledger on your own infrastructure, with evidence files you can regenerate.

Not yet: a hosted version, a web wizard to connect an account, a standing approval queue with notifications, alerting, spend history per agent, and multi-account or single sign-on. See the Safety model for what is and is not claimed.
