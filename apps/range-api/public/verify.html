Independent verifier

Runs on a different VM, in a different region, with a different read-only key. It lists the live Vultr account twice, 3 seconds apart, and compares it to the broker's hash-chained ledger export and to an owner-written baseline. It re-runs the policy engine on what Vultr reports, so a forged ALLOW row for a plan the floor forbids still turns RED. A Vultr error, a stale export or a missing baseline shows DEGRADED, never GREEN.

Stated limits

  • Point-in-time: a resource created and destroyed between two polls is not seen. A destroy is visible within about 0.8 s, so a rogue VM is declared only when it is present at both polls. Create-then-delete inside one gap is not prevented and not detected.
  • The ledger is the broker's own record. The verifier checks its hash chain, its freshness and that it only ever grows, but a broker that lies consistently from its first row is caught only by the live comparison and the policy re-run.

Not covered

What the verifier cannot see with a view-only key, and says so on every verdict:

  • Firewall groups: the view-only key gets 403 on /firewalls, so the per-session playground firewall group is not compared (it is a VPC now, which is).
  • Object Storage buckets and object versions: 403 on /object-storage.
  • Dollar ceiling and session spend: the export carries no session state. Plan, region, label and scope rules are replayed on live state; the dollar rule is the broker's.

Covered: instances, VPCs and container registries.
