Concepts in plain words

Plumbline has a small vocabulary. These are the words you will meet on the other pages.

Broker
The one process that holds the cloud credentials. The agent never does; it can only ask the broker.
Policy engine
Code that answers every request with ALLOW, ESCALATE or DENY and the rule that decided it. It is a function, not a model.
Floor
The production rules nobody can edit from the sandbox. Your own policy copy can be stricter or looser, but the floor is always applied too, and the most restrictive answer wins.
Escalate
Held for a person. Nothing runs until someone approves it. An approval is bound to that decision and a one-time token, and is re-checked against the live account when you approve.
Verifier
A second host in another region with a read-only key. It reads the live account and compares it to the ledger. GREEN, RED naming the resource, or DEGRADED when it cannot tell.
Reconcile
The verifier comparing what policy says should exist with what Vultr shows. No difference means GREEN.
Watchdog
Runs next to the verifier. If the broker stops renewing its lease it destroys the agent's workers and playgrounds, and nothing else.
Tier
The access level of the key the agent uses. Observer is read-only, and Vultr itself refuses writes.
Spend limit
A dollar limit per session and overall that the agent cannot raise. It is checked before any call to Vultr.
Kill switch
An owner-signed switch on the broker that refuses every mutating action until the owner clears it.
Bond
A small risk budget per session. An approved delete with no restore point burns it, and while it is low, new provisions are refused.
Rewind
The one live undo: Object Storage keeps versions, so a deleted object can be restored.
Ledger
The append-only record of every decision. Only the engine path can write a row.
Rung and gate
A rung is one safety claim. Its gate is the live test that proves it against the real account and writes an evidence file.
Compliant-operator mode
The demo model is instructed to follow the attacker's request. That is deliberate: it makes the policy engine, not the model's own caution, the thing being tested.

How a policy rule is written

Policy is a YAML file you can review, test and version. Each rule has an id, an effect, a priority, a match and optional conditions. This is a real rule from the production floor:

- id: floor-prod-immutable
  effect: deny            # allow | escalate | deny
  priority: 95            # higher wins within a layer
  match:                  # which requests this rule is about
    verb: [delete, update]
    class: [instance, firewall_group, vpc, registry]
    label_prefix: [plumbline-prod-, plumbline-infra-]
  when: {}                # optional conditions on state (spend, bond, kill switch)
  reason: "production floor: not editable without a signed approval"

Two layers are evaluated for every request: the production floor, which is signed and immutable, and the session policy, which you may edit in your own sandbox copy. The most restrictive answer wins. The Policy page lets you edit the sandbox copy of the demo and see the effect.
