Run Plumbline on your own Vultr account

The demo runs on an account we own. Everything you see there is the same software you can run on yours: the policy engine, the broker that holds the keys, the hardened sandbox, the second-region verifier and the watchdog. The status strip at the top of every page, including this one, shows our demo account.

1. Before you start

  • A Vultr account with an owner API key, and credit or a card for two small VMs.
  • A machine with Node 24 and git to run the setup commands from.
  • Vultr today. The policy engine judges verbs, resource classes and targets, so another cloud needs an adapter, not a new engine. Only the Vultr adapter exists.

What gets created

  • Broker VM (one region): the public app, the broker that holds every key, and the sandbox runner. Three services.
  • Verifier VM (a second region): the verifier and the watchdog, each with its own scoped key.
  • A protected production resource the agent must not touch, and a versioned Object Storage bucket for the undo demo.
  • Six IP-locked sub-user keys, one per access tier, each with an explicit expiry.

2. Set it up

  1. Clone the repository and install: git clone https://github.com/dmustapha/plumbline && cd plumbline && npm ci
  2. On your machine, with your owner API key in the environment, create the infrastructure: npm run bootstrap:range. It is idempotent and prints only a summary.
  3. Install the systemd units from ops/systemd/ on the two VMs and start them.
  4. Sign your production policy with your own key: npm run sign-policy. Production changes need that signature.
  5. Prove each rung on your account: npm run gate -- l1 through l7. Each writes an evidence file.
  6. When you are done: npm run teardown lists everything it created and deletes only with --yes.

3. Where your keys live

  • Only on the broker VM, in a root-owned environment file. Never in the agent, the sandbox or the browser.
  • Your owner key never goes on a VM. Every service refuses to start if it finds one.
  • The agent talks to the broker over one route. It can ask; it cannot read.

4. Write your policy

Rules are data in a YAML file you can review, test and version. The production floor is signed and immutable; your session policy can be stricter or looser, and the most restrictive answer wins. See Concepts for the rule format, and try it on the Policy page of the demo.

5. Plug in your agent

The agent never holds a cloud credential. It sends its actions to the broker, and the broker answers ALLOW, ESCALATE or DENY. Today the bundled operator is the agent; to use your own, route its cloud calls through the broker. The contract is on Integrate an agent. There is no packaged SDK or MCP server yet.

6. Approvals

When a rule says ESCALATE, the action is held. An approval is bound to that decision and a one-time token, is re-checked against the live account at the moment you approve, and cannot override a floor DENY. Today approvals are handled on the demo page for the session that made the request; there is no standing queue or notification yet.

7. Audit your account

The verifier ships as a command that reads your account with a view-only key and a ledger export, and writes nothing to Vultr:

PLUMBLINE_VERIFY_KEY=<view-only key> npx tsx apps/verifier/src/cli.ts --ledger ledger.json --baseline baseline.json
# exit 0 GREEN, 1 RED, 2 DEGRADED

The broker serves a signed ledger export at /ledger/export. The same check runs live on the Reconcile page.

8. Status and roadmap

Today: the engine, broker, sandbox, verifier, watchdog and ledger on your own infrastructure, with evidence files you can regenerate.

Next layer, not in this release: a hosted version, a web wizard to connect an account, a standing approval queue with notifications, alerting, spend history per agent, an SDK or MCP server, multi-account and single sign-on, other clouds.
